## 1. 속도 제한이 한 번도 적용된 적이 없다

가장 오래 숨어 있던 문제다.

**증상** — 서버 기동 로그에 경고가 12줄(로봇 2대 × 모터 6개) 찍힌다.

```
⚠ shoulder_pan Max_Velocity 실패:
   "Address for 'Max_Velocity' not found in sts3215 control table."
```

**원인** — `apply_speed_settings()` 가 쓰던 `Max_Velocity` 는 STS3215 컨트롤 테이블에
**존재하지 않는 레지스터 이름**이다. 라파에서 직접 확인했다.

```python
from lerobot.motors.feetech.tables import STS_SMS_SERIES_CONTROL_TABLE as T
# 존재:  Goal_Velocity, Maximum_Velocity_Limit, Acceleration, Torque_Limit ...
# 없음:  Max_Velocity
```

**왜 여태 못 봤나** — 쓰기가 `try/except` 안에 있어 예외가 삼켜졌고, 바로 다음 줄에서
성공한 것처럼 보이는 로그를 찍었다. `Acceleration` 은 이름이 맞아서 정상 적용됐기 때문에
"속도 설정이 먹고는 있구나" 로 보였다.

```
🎚️ 초기 속도: velocity=800, accel=50     ← velocity 는 사실 적용 안 됨
```

**수정** — `Max_Velocity` → `Goal_Velocity`.

**부작용 (중요)** — 이 수정으로 `800` 이 **처음으로 실제 적용**됐다. UI 속도 슬라이더 범위가
`0~3000` 이므로 800 은 최대치의 27% 다. 그전까지 사실상 무제한으로 돌던 것이 갑자기
느려졌다. 10번 항목과 직접 관련이 있다.

## 2. 서버 기동 시 팔이 스스로 움직인다

**조건** — 전원을 껐다 켜서 팔이 주저앉은 상태에서 서버를 기동할 때.

**원인** — `connect_robot()` 이 `enable_torque()` 를 호출하기 전에 `Goal_Position` 을
현재 위치로 맞추지 않았다. 모터에 남아 있던 예전 목표로 팔이 스스로 이동한다.

같은 안전장치가 `handle_teach()` 에는 **이미 있었다.** 기동 경로에만 빠져 있었다.

```python
# handle_teach() — 있음
# ⚠️ 토크를 켜기 전에 목표를 현재 위치로 맞춰야 한다.
pos = int(bus.read("Present_Position", name, normalize=False))
bus.write("Goal_Position", name, pos, normalize=False)

# connect_robot() — 없었음
bus.enable_torque()
```

**수정** — 기동 경로에도 같은 동기화 루프를 넣었다. 이제 주저앉은 자세 그대로 토크가 잡힌다.
세우는 것은 그 다음에 **홈으로 이동**으로 한다.

> `pkill -9` 로 팔이 안 떨어지게 만든 것(README 참조)과 짝이 되는 수정이다.
> 그쪽은 *끌 때* 안 떨어지게, 이쪽은 *켤 때* 안 튀게 한다.

## 3. 그리퍼 수동 조작 — 시도했다가 되돌렸다

**처음 판단** — `handle_teach()` 가 그리퍼를 명시적으로 건너뛰고 있었다.

```python
if name == 'gripper':
    continue          # 그리퍼는 손으로 만지지 않는다
```

그리퍼는 중력으로 무너질 것이 없어 완전 해제해도 안전하고, 손으로 벌리고 오므린 상태까지
녹화되면 좋겠다는 요구가 있어 `TEACH_FREE` 에 넣고 건너뛰기를 제거했다.

**실물 확인 결과 — 손으로 조작이 불가능했다.** 토크를 완전히 해제해도 그리퍼가 벌어지지도
오므라들지도 않는다. 그리퍼도 같은 1:345 감속이라 팔 관절과 똑같이 역구동이 안 된다.
README 에 이미 적혀 있던 "손으로 밀어도 안 꺾임" 이 그리퍼에도 그대로 적용된다는 것을
이번에 확인했다.

**최종 결정 — 슬라이더 전용.** 풀어봐야 손 조작은 안 되면서 슬라이더만 못 쓰게 되므로
(4번 참조), 그리퍼는 수동모드에서도 토크를 유지한다. `TEACH_FREE` 에서 다시 뺐다.

```python
# 그리퍼는 일부러 뺐다. 풀어도 손으로 조작할 수 없다.
TEACH_FREE = ("shoulder_pan", "wrist_roll", "wrist_flex")
```

수동모드 중에도 그리퍼 슬라이더가 그대로 동작한다.

## 4. 그리퍼 토크 자동복구가 피드백 루프를 만들었다

3번을 하고 나니 **수동모드에서 그리퍼 슬라이더가 안 먹는** 문제가 따라왔다.
토크가 꺼진 서보는 `Goal_Position` 쓰기를 무시하기 때문이다.

**첫 시도 (실패)** — `handle_set_position()` 에서 그리퍼 명령이 오면 토크를 되살리게 했다.
이게 루프를 만들었다.

```
손으로 그리퍼를 벌림
  → 실물 위치 변화
  → Unity 가 폴링으로 읽어 모델 갱신
  → 송신 루프가 바뀐 값을 set_position 으로 전송
  → 서버가 "슬라이더 명령"으로 오인해 토크 ON
  → 즉시 되잡힘
```

명령의 출처(사람이 민 결과냐, 슬라이더냐)를 서버가 구분할 수 없다는 게 핵심이다.
둘 다 같은 `set_position` 으로 들어온다.

**수정** — 서버가 수동모드 상태를 기억하게 했다.

```python
TEACH_ON = {"robot1": False, "robot2": False}   # handle_teach 가 갱신

# handle_set_position
if motor == 'gripper' and TEACH_ON.get(rname):
    continue        # 수동 중 그리퍼 명령은 통째로 무시
```

**최종 정리** — 3번에서 손 조작이 애초에 불가능하다는 것이 확인되면서 이 딜레마 자체가
사라졌다. 그리퍼를 `TEACH_FREE` 에서 빼자 토크가 유지되고, 되잡힐 일이 없으니 위 무시 처리도
불필요해져 함께 제거했다. **수동모드 중에도 그리퍼 슬라이더가 정상 동작한다.**

남은 교훈은 하나다. 서버는 `set_position` 만 보고 **명령의 출처를 구분할 수 없다.**
사람이 민 결과가 폴링을 타고 되돌아온 값과, 슬라이더로 준 값이 같은 모양으로 도착한다.
앞으로 관절에 대해 비슷한 것을 하려면 전용 명령을 따로 파야 한다.

## 5. 수동모드 토크 상태를 신뢰할 수 없었다

`handle_teach()` 는 **자기가 쓴 값**을 로그에 찍었다. 실제로 반영됐는지는 알 수 없다.
"수동인데 토크가 안 빠진 것 같다" 를 로그만 보고 판단할 수 없어서, 쓴 뒤에 레지스터를
되읽어 함께 남기도록 했다.

```
🔓 수동모드 ON — robot1: {'shoulder_pan': 'free(실제 TE=0 TL=500)', ...}
```

1번과 같은 종류의 함정(쓰기는 실패했는데 로그는 성공처럼 보임)을 두 번 겪지 않으려는 조치다.

## 6. `PincOpenSafety` 가 그리퍼를 막는다고 의심 — 원인 아님

그리퍼 슬라이더가 안 먹을 때 1순위 용의자였다. `SOArmRealController.Update()` 의
송신 직전에 게이트가 있고, 차단되면 조용히 `continue` 한다.

```csharp
if (!PincOpenSafety.TryApprove(0f, out _)) { ... continue; }   // 보내지 않는다
```

**조사 결과 원인이 아니다.** `RealGripperEnabled` 는 기본값이 `true` 이고,
저장소 전체에서 이를 `false` 로 바꾸는 코드가 **한 곳도 없다.** 게이트는 항상 열려 있다.

```
$ grep -rn "RealGripperEnabled\s*=" Assets/Script
PincOpenSafety.cs:57:  public static bool RealGripperEnabled = true;    ← 선언 한 줄뿐
```

실제 원인은 4번이었다.

## 7. Unity 컴파일 경고

수동모드·녹화 코드는 **작성 후 한 번도 컴파일된 적이 없었다.** 에러는 없었고 경고만 나왔다.

| 경고 | 조치 |
|---|---|
| `CS0618: FindObjectsByType<T>(FindObjectsSortMode)` 사용 중단 (`SmartFactoryUI_v3_4.cs:312`) | 파라미터 제거. 원래 `None` 이라 동작 동일. 저장소 내 다른 사용처 없음 |
| `Input Manager is marked for deprecation` | **조치 안 함.** 프로젝트 전역 안내이고 이번 코드와 무관. Input System 으로 옮기면 기존 입력 처리를 전부 다시 짜야 한다 |

## 8. PC 시계가 9시간 느리다 — 미조치

처음에는 라파가 틀린 줄 알았으나 **반대였다.** 외부 기준시간을 받아 대조해서 확정했다.

| 대상 | 값 | 판정 |
|---|---|---|
| 외부 기준 (HTTP `Date`) | `Sat, 01 Aug 2026 23:00:44 GMT` | 기준 |
| 라파 UTC | `2026-08-01 23:00:46 UTC` | ✅ 일치 |
| 라파 로컬 | `2026-08-02 08:00:46 KST` (Asia/Seoul, NTP 동기화됨) | ✅ 정확 |
| PC 로컬 | `2026-08-01 23:01` | ❌ **9시간 느림** |

PC 표준시간대는 `Korea Standard Time` 으로 정상이다. **시계 값 자체가 틀렸다.**
원인은 `w32time` 서비스가 중지 상태여서 자동 동기화가 아예 돌지 않은 것.

**조치 방법** (관리자 권한 PowerShell 필요, 아직 실행 안 함)

```powershell
Set-Service w32time -StartupType Automatic
Start-Service w32time
w32tm /resync /force
```

**영향** — 이 상태로 커밋하면 커밋 타임스탬프가 9시간 과거로 찍혀 이전 커밋과 순서가 엉킨다.
커밋 전에 맞추는 것이 좋다.

## 9. 라파 SSH 비밀번호 반복 입력 — 해결

배포·기동·로그 확인을 매번 비밀번호로 하면 작업이 끊긴다. 기존 키를 등록했다.

- 키: `~/.ssh/id_ed25519` (2026-05-09 생성). 새로 만들지 않았다
- OpenSSH 로는 비밀번호를 자동 입력할 수 없어 PuTTY `plink` 를 경유했다
- plink 는 호스트 키가 캐시에 없어 `-batch` 에서 거부한다. **지문을 그냥 받아들이지 않고**
  OpenSSH `known_hosts` 에 이미 저장된 값과 대조한 뒤 진행했다

```
known_hosts : SHA256:ZmeNKBzMu3DWsRG30nvyHcdsne9fSFyT00ROHLZRsVc
plink 보고  : SHA256:ZmeNKBzMu3DWsRG30nvyHcdsne9fSFyT00ROHLZRsVc   ← 일치
```

이후로는 `ssh` / `scp` 가 비밀번호 없이 동작한다.

## 10. 움직이다 중간에 멈춘다 — **미해결**

**증상** — 명령을 주면 움직이다가 도중에 멈춘다.

**확인된 것**
- 서버 로그에 에러·예외·차단 기록이 **하나도 없다**
- TCP 연결은 ESTABLISHED 로 정상 유지
- 수동모드는 이 증상이 난 연결에서 켜진 적이 없다

**1순위 가설** — 1번 수정으로 `Goal_Velocity=800` 이 처음 적용된 것. 그전까지 무제한으로
돌던 것이 최대치의 27% 로 묶였으니, 크게 느려진 것을 "가다가 멈춘다" 로 볼 수 있다.

**다음에 할 확인** — 재시작 없이 UI 속도 슬라이더(`0~3000`)를 2500 정도로 올리거나
`🐇` 프리셋을 눌러 A/B 한다. `ApplySpeedToServer()` 가 바로 반영한다.

| 결과 | 진단 |
|---|---|
| 끝까지 감 | 속도 제한이 원인. 기본값을 다시 정하면 된다 |
| 여전히 멈춤 | 속도 문제가 아니다. 서보 과부하 보호를 의심하고 `Present_Load` 를 본다 (10비트 2의 보수 주의) |

## 이월된 미해결 항목

이번 세션에서 건드리지 않았다. 출처는 이전 작업 메모.

- 로봇2 `wrist_flex` 0점 잔차 **약 10.5°**

## 아직 검증하지 못한 것

정직하게 남긴다. 이번 세션에서 **실물로 확인하지 못한** 항목이다.

- 수동모드에서 손으로 팔(`shoulder_pan` / `wrist_roll` / `wrist_flex`)이 실제로 밀리는지.
  5번 되읽기 로그를 아직 못 봤다. 그리퍼가 1:345 때문에 안 밀렸으므로 이 셋도 같은 이유로
  뻑뻑할 가능성이 있다
- 그리퍼 슬라이더가 수동모드 중에도 먹는지 (3번 최종 수정 후 미확인)
- 녹화 → 재생 한 사이클
- 2번 수정이 실제로 팔이 튀는 것을 막는지 (전원 재투입 상황을 재현하지 않았다)
